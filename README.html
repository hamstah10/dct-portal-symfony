TFD CRM - Funktionsuebersicht

Stand: 12.03.2026

Diese Datei dokumentiert die aktuell implementierten Funktionen des CRM in dieser Symfony-8-Anwendung.

1. Systemueberblick

  • Framework: Symfony 8 + Doctrine ORM + EasyAdmin.
  • Hauptbereich: /admin (nur ROLE_ADMIN).
  • Login: Formular-Login ueber /login, danach Admin-Dashboard.
  • Frontend: / (Redirect), /chiptuning (Fahrzeugdatenbank), /chiptuning/api-test, /chiptuning/profitcalculator.
  • Kernmodule: Kunden, Support, Websites, Media, Fahrzeuge, Profit Calculator, Dyno, VIN Decoder, Lexware, Verwaltung, Credits, API, Automationen.

1.1 Systemarchitektur

  • Monolithische Symfony-8-Anwendung im MVC-Pattern.
  • Admin-UI ueber EasyAdmin-CRUDs in src/Controller/Admin.
  • Domainthemen in src/Entity, src/Repository, src/Service, Events/Subscribers in src/EventSubscriber.
  • Zugriffskontrolle basiert auf Symfony Security (Rollen) und Seitenrechten.
  • Seitenrechte werden ueber AdminPageAccess + AdminPageAccessService + AdminPageAccessSubscriber enforced.
  • Seiten- und Menuestruktur wird zentral in AdminPageRegistry gepflegt (inkl. Unterseiten-Vererbung).
  • Benutzerstatus (aktiv/inaktiv) wird ueber UserStatusChecker im Login erzwungen.
  • Datenbankaenderungen erfolgen ueber Doctrine-Migrations in migrations.

2. Dashboard (Admin Startseite)

  • KPI-Karten fuer Kunden, Software, Abos, offene/abgeschlossene Auftraege, Erfolgsquote, Monatsumsatz.
  • Tabelle mit aktuellen Auftraegen (Kunde/Firma/Fahrzeug/Status/Zeit).
  • Chart-Bereich mit Projektstatistik und Umsatzentwicklung.
  • Auftragsstatus-Progress-Balken (eingegangen, in Bearbeitung, abgeschlossen, abgelehnt).
  • Abo-Status-Chart.
  • Kunden-pro-Firma-Chart.
  • Kundenkarte (Map) mit Marker-Auswertung.
  • Team-/Kommunikationsbereich mit letzten Nachrichten je Firma.

3. Kunden-Modul

3.1 Kunden

  • Vollstaendige Kundenverwaltung (Stammdaten, Adresse, Kontakt, Newsletter, Sperrstatus).
  • Firmenzuordnung je Kunde.
  • Kundenbild-Upload.
  • Passwortfeld im Admin mit sicherem Hashing (password_hash) bei Anlage/Aenderung.
  • Kundenindex mit Firmenkuerzel-Badges (u. a. TFD/CPT) und Kundenzahlen pro Firma.

3.2 Software

  • Softwareverwaltung mit Version, Beschreibung, Preis, Aktiv-Status.
  • Mehrfachoptionen (TYPO3, Wordpress).
  • Mehrfach-Bildupload mit Galerievorschau.
  • Zuordnung zu mehreren Demos.

3.3 Abos

  • Aboverwaltung pro Kunde.
  • Zwei Modellarten:
  • Software-basiert.
  • Paket + Laufzeit (Abo-Auswahl + Preisstaffel).
  • Validierung: Es muss genau eine der beiden Varianten gesetzt sein.
  • Zahlweise monatlich/jaehrlich.
  • Automatische Preisberechnung aus Preisstaffel inkl. Einrichtungsgebuehr.
  • Aboindex mit Umsatz-Charts (Abo-Umsatz + Setup-Umsatz pro Monat).

3.4 Auftraege

  • Auftragsverwaltung mit:
  • Statusworkflow (eingegangen, in_bearbeitung, abgeschlossen, abgelehnt).
  • Fahrzeugdaten, Tuning-Setup, Stage, Device.
  • Ursprungsdatei (Base64), Dateigroesse, Dateiname.
  • Upload einer Fertig-Datei (Dropzone im Admin).
  • Karten/Statistik im Auftragsindex (heute, gestern, 7 Tage, Statuszahlen).
  • Firmenbadge-Anzeige (TFD/CPT) in Listenansicht.
  • Live-Benachrichtigungsstream fuer neue Auftraege via SSE (/admin/notify/orders).
  • Webhook-Ausloesung bei Statusaenderungen (order.status_changed).

3.5 Kunden-Credits

  • Credit-Transaktionen pro Kunde (Aufladung, Verbrauch, manuelle Korrektur, Storno/Umkehr).
  • Saldo-Vorher/Nachher Speicherung je Transaktion.
  • Admin-CRUD fuer Transaktionen inkl. Beschreibung und Ersteller.

5.2 Sniffer

  • Beliebig viele Sniffer-Konfigurationen:
  • Name.
  • Verzeichnis/URL.
  • Unterordner scannen ja/nein.
  • Aktivstatus.
  • Beschreibung.
  • Start eines Sniffer-Laufs per Button direkt aus der Liste.
  • Jeder Lauf wird als eigener Datensatz gespeichert:
  • Start/Ende.
  • Status (running, success, failed).
  • Fehlertext.
  • Dauer.
  • Bearbeitete/Gesamt/gefunde Seiten.
  • Quelle (aufgeloestes Verzeichnis oder Basis-URL).
  • Live-Fortschrittsanzeige direkt oben auf der Sniffer-Indexseite:
  • Progressbar.
  • Statusbadge.
  • Bearbeitungszaehler.
  • Link zum Lauf.
  • Link zu geparsten Seiten.
  • Sniffer verarbeitet lokale HTML-Dateien und HTTP-Seiten:
  • Dateiendungen .html/.htm/.xhtml.
  • Optional rekursiv.
  • Deduplizierung von Seiten (kein mehrfaches Speichern derselben Seite im Lauf).
  • HTML-Parsing pro Seite:
  • title, erste h1, meta description.
  • Body-Text-Laenge, Dateigroesse.
  • Strukturierte Parser-Daten (meta, headings, assets, links, forms, tagCounts, Content-Werte).
  • Vollstaendige HTML-Quelle wird gespeichert.
  • Screenshot je Seite:
  • Remote ueber Chromium Headless, Fallback mShots.
  • Lokal ueber file://-Capture.
  • Geparste Seiten:
  • Eigene CRUD-Ansicht mit Filter auf runId.
  • Screenshot-Preview.
  • Detailansicht inkl. JSON-Parserdaten und HTML-Quelltext.
  • Mediengalerie im Lauf-Detail (Grid mit Preview, Admin-Link, Seiten-Link falls oeffentlich erreichbar).

15. API (extern)

15.1 Auth API

  • POST /api/auth/login
  • POST /api/auth/refresh
  • GET /api/auth/me
  • POST /api/auth/logout
  • Erzeugt Access/Refresh-Tokens je Kunde (Session/DeviceName) mit Ablauf und Widerruf.

15.2 Customer API (Systemtoken)

  • GET /api/customers
  • GET /api/customers/{id}
  • POST /api/customers
  • PUT /api/customers/{id}
  • PATCH /api/customers/{id}
  • DELETE /api/customers/{id}
  • Authentifizierung per System-API-Token (Bearer).

15.3 Order API

  • POST /api/orders
  • Validiert Pflichtfelder inkl. Datei/Base64 und Fahrzeugdaten.
  • Akzeptiert Systemtoken oder gueltiges Customer-Access-Token.
  • Erstellt Auftragsdatensatz und triggert Webhook order.created.

15.4 Fahrzeugdatenbank API

  • Authentifizierung erforderlich mit zwei Headern:
  • Authorization: Bearer <API_TOKEN>
  • X-Token-Id: <TOKEN_ID>
  • Token-Verwaltung: Verwaltung -> API Tokens.
  • Token muss aktiv und gueltig sein (Ablaufdatum optional konfigurierbar).
  • GET /api/fahrzeugdatenbank
  • GET /api/fahrzeugdatenbank/types
  • GET /api/fahrzeugdatenbank/brands/{typeId}
  • GET /api/fahrzeugdatenbank/series/{brandId}
  • GET /api/fahrzeugdatenbank/models/{seriesId}
  • GET /api/fahrzeugdatenbank/engines/{modelId}
  • GET /api/fahrzeugdatenbank/engine-details/{engineId}
  • Engine-Details liefern:
  • stages (alle aktiven Stages des Motors).
  • ecus inkl. options (engineweit, nicht pro Stage getrennt).
  • POST /api/fahrzeugdatenbank/track
  • OpenAPI JSON nur fuer die Fahrzeug-API: docs/openapi-vehicle.json (OpenAPI 3.0.3).

15.5 Dyno / Telemetrie API

  • Oeffentliche Telemetrie-Endpunkte:
  • GET|POST|DELETE /api/vehicles (Dyno-Fahrzeuge, inkl. Aktivierung).
  • GET|POST|DELETE /api/trips + CSV-Export GET /api/trips/export/csv.
  • GET|POST|DELETE /api/dtcs inkl. Batch-Import POST /api/dtcs/batch.
  • CRM-geschuetzte Endpunkte (Bearer Token via api_token oder DB-Token):
  • GET|POST|PUT|DELETE /api/crm/customers inkl. Detail mit Fahrzeug/Trips.
  • GET|DELETE /api/crm/trips + GET /api/crm/trips/{id}/datapoints.
  • GET|POST|DELETE /api/crm/sprints + GET /api/crm/sprints/bestlist.
  • GET /api/crm/analytics/overview|per-vehicle|per-mode.

15.6 Tuningfux API (Fahrzeugdaten fuer externe Systeme)

  • Authentifizierung: Bearer Token (env api_token oder API-Token aus DB).
  • GET /api/tuningfux/types
  • GET /api/tuningfux/brands/{typeId}
  • GET /api/tuningfux/series/{brandId}
  • GET /api/tuningfux/models/{seriesId}
  • GET /api/tuningfux/engines/{modelId}
  • GET /api/tuningfux/engine-details/{engineId}

16. Webhooks (Outgoing)

  • Admin-Konfiguration unter Verwaltung -> Webhooks.
  • Unterstuetzte Events:
  • order.created
  • order.status_changed
  • Optionales HMAC-Signing:
  • Header X-Webhook-Timestamp
  • Header X-Webhook-Signature: sha256=<hmac>
  • Zustellstatus wird am Endpunkt gespeichert (letzter Status, Fehler, Zeitpunkt).

22. Projektstruktur (Auszug)

  • src/Entity/ - Doctrine Entities (Attribute Mapping)
  • src/Controller/Admin/ - EasyAdmin CRUD Controller
  • src/Repository/ - Datenbankabfragen
  • src/Service/ - Business-Logik
  • migrations/ - Doctrine Migrations
  • templates/ - Twig Templates

23. Code Style (Auszug)

  • PHP 8.4+ mit Type Hints, kein schliessendes ?>
  • Entities mit #[ORM\Entity] / #[ORM\Column], Setter geben static zurueck
  • Collections: @var Collection<int, Entity>, ArrayCollection, fluent add/remove
  • CRUD Controller: AbstractCrudController, #[AdminCrud], configureFields()
  • Formatierung: 4 Spaces, LF, UTF-8
  • Formulare: EasyAdmin Field-Klassen (TextField, AssociationField), .onlyOnIndex(), .hideOnForm()
